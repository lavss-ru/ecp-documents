# ECP Documents

> Архитектура плагина.

**Статус:** Draft  
**Версия документа:** 1.0  
**Дата:** 2026-07-28

---

## 1. Назначение документа

Документ описывает архитектуру плагина ECP Documents.

Его цель — объяснить структуру проекта, взаимодействие компонентов и основные архитектурные решения.

Документ не описывает пользовательский интерфейс и не заменяет спецификацию проекта.

---

## 2. Основные принципы

Архитектура плагина строится на следующих принципах:

- один плагин — одна задача;
- использование стандартного API WordPress;
- минимальное количество собственных сущностей;
- отсутствие избыточных абстракций;
- простота сопровождения;
- совместимость с будущими версиями WordPress.

Каждый компонент должен иметь одну чётко определённую ответственность.

---

## 3. Общая структура

Плагин состоит из нескольких независимых компонентов.

- **Core** — запуск плагина и регистрация компонентов.
- **Admin** — интеграция с редактором WordPress.
- **Document** — описание документа с электронной подписью.
- **Media** — работа с PDF- и SIG-файлами через медиатеку WordPress.
- **Frontend** — отображение документа на сайте.

Каждый компонент отвечает только за свою область ответственности.

---

## 4. Хранение данных

Плагин не создаёт собственое хранилище документов.

Для хранения файлов используются стандартные возможности WordPress.

- PDF-файлы хранятся в медиатеке.
- SIG-файлы хранятся в медиатеке.

Документ с электронной подписью представляет собой логическую связь между выбранными файлами и отображается пользователю как единый элемент.

---

## 5. Интеграция с WordPress

Плагин использует стандартные механизмы WordPress:

- Hooks;
- Actions;
- Filters;
- Media Library API;
- TinyMCE API (Classic Editor).

Использование сторонних библиотек допускается только при наличии объективной необходимости.

---

## 6. Расширяемость

Архитектура должна позволять развитие проекта без изменения существующей модели работы.

В частности, должна быть возможность:

- добавить поддержку Gutenberg;
- изменить внешний вид документа;
- расширить отображение документа.

При этом базовая модель «Документ с ЭП» должна оставаться неизменной.

---

## 7. Что не входит в архитектуру

Архитектура плагина сознательно не предусматривает:

- систему управления документами;
- каталог документов;
- собственую файловую систему;
- криптографическую проверку электронной подписи;
- интеграцию с внешними сервисами.

Эти ограничения являются частью концепции проекта и позволяют сохранить простоту реализации.

---

## 8. Принцип развития

Любое изменение архитектуры должно соответствовать следующим требованиям:

- не усложнять проект без необходимости;
- использовать стандартные возможности WordPress;
- сохранять совместимость с существующим функционалом;
- не нарушать основной принцип проекта:

> **Один плагин — одна задача.**
