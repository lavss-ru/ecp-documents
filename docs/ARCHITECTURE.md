# Назначение документа

Этот документ описывает архитектуру плагина **ECP Documents**.

Его цель — объяснить устройство проекта, взаимодействие компонентов и основные архитектурные принципы.

Документ предназначен для:

- разработчиков;
- AI-помощников;
- сопровождения проекта в будущем.

---

# Общая архитектура

Плагин построен на стандартной архитектуре WordPress и не использует собственных нестандартных механизмов там, где существуют штатные возможности платформы.

Основные принципы:

- использовать WordPress API;
- минимизировать количество собственного кода;
- избегать лишних зависимостей;
- соблюдать совместимость с будущими версиями WordPress.

# Назначение каталогов

## assets/

Статические ресурсы проекта.

Содержит:

- CSS;
- JavaScript;
- изображения.

Эти файлы используются административной частью и фронтендом.

---

## docs/

Документация проекта.

Здесь находятся документы:

- HANDOFF.md
- ARCHITECTURE.md
- SPECIFICATION.md
- DECISIONS.md
- ROADMAP.md
- CONTRIBUTING.md
- AI_CONTEXT.md

---

## languages/

Файлы локализации.

Все пользовательские строки должны быть готовы к переводу.

---

## src/

Основная PHP-логика проекта.

Все классы располагаются здесь и загружаются через Composer (PSR-4).

---

## templates/

HTML-шаблоны административного интерфейса.

PHP-классы не должны содержать большие HTML-блоки.

Разметка выносится в templates.

---

## vendor/

Автоматически создаётся Composer.

Не редактируется вручную.

---

# Точка входа

Главной точкой входа является файл:

```
ecp-documents.php
```

Он отвечает за:

- загрузку Composer;
- загрузку классов;
- инициализацию плагина;
- регистрацию необходимых хуков WordPress.

Вся бизнес-логика должна находиться вне этого файла.

---

# Composer

Для автозагрузки используется Composer.

Стандарт:

- PSR-4

Все классы располагаются внутри пространства имён проекта.

---

# Жизненный цикл плагина

Упрощённая схема работы:

```
WordPress

↓

Загрузка плагина

↓

ecp-documents.php

↓

Composer Autoload

↓

Инициализация Plugin

↓

Регистрация хуков

↓

Работа административной части

или

Работа фронтенда
```

---

# Административная часть

Административная часть предназначена для формирования shortcode.

Пользователь:

```
Нажимает

↓

Добавить документ

↓

Выбирает PDF

↓

Выбирает SIG

↓

Получает shortcode

↓

Shortcode вставляется в редактор
```

Административная часть не должна заниматься выводом документа на сайте.

---

# Работа с Media Library

Все документы выбираются исключительно через стандартную Media Library WordPress.

Используются:

- PDF
- SIG

Плагин не хранит собственные копии файлов.

---

# Хранение данных

Во внутренних структурах используются только attachment_id.

Не рекомендуется хранить:

- URL;
- абсолютные пути;
- относительные пути.

Использование attachment_id обеспечивает:

- переносимость;
- совместимость;
- корректную работу после смены домена;
- использование стандартного WordPress API.

---

# Формирование shortcode

После выбора документов создаётся shortcode.

Пример:

```text
[ecp_document title="Приказ №1" pdf_id="123" sig_id="456"]
```

Этот shortcode является публичным API плагина.

Его структура должна оставаться стабильной.

---

# Frontend

При открытии страницы WordPress:

```
Shortcode

↓

Парсер WordPress

↓

Обработчик shortcode

↓

Получение attachment_id

↓

Получение ссылок через WordPress API

↓

Формирование HTML

↓

Вывод пользователю
```

Frontend не должен обращаться к файлам напрямую.

---

# Разделение ответственности

Каждый компонент проекта отвечает только за свою задачу.

Например:

- PHP — бизнес-логика.
- Templates — HTML.
- CSS — оформление.
- JavaScript — интерактивность.

Следует избегать смешивания этих обязанностей.

---

# Расширяемость

Архитектура должна позволять добавлять новые возможности без изменения существующего кода.

Например:

- поддержку Gutenberg;
- дополнительные форматы документов;
- настройки отображения;
- новые варианты оформления.

При этом существующий shortcode должен продолжать работать.

---

# Зависимости

Следует максимально использовать:

- WordPress Core;
- WordPress API;
- Composer.

Добавление сторонних библиотек допускается только при наличии объективной необходимости.

---

# Производительность

Плагин ориентирован на минимальную нагрузку.

Основные принципы:

- не выполнять тяжёлые операции без необходимости;
- не делать лишние SQL-запросы;
- использовать WordPress API;
- не загружать ресурсы на страницах, где они не нужны.

---

# Совместимость

При разработке необходимо сохранять совместимость с:

- WordPress;
- PHP, поддерживаемыми WordPress;
- Classic Editor.

Поддержка Gutenberg является дополнительной возможностью, а не обязательным требованием первой версии.

---

# Архитектурные принципы

Проект придерживается следующих принципов:

1. Простота.
2. Предсказуемость.
3. Минимум зависимостей.
4. Использование стандартных возможностей WordPress.
5. Читаемый код.
6. Простота сопровождения.

Если существует несколько вариантов реализации, предпочтение отдаётся самому простому решению.
