>
> **Status:** Active

---

# Назначение документа

Этот документ описывает правила участия в разработке проекта **ECP Documents**.

Он определяет единый подход к:

- разработке новых функций;
- исправлению ошибок;
- оформлению коммитов;
- изменению архитектуры;
- обновлению документации.

Соблюдение этих правил позволяет сохранять проект понятным, предсказуемым и удобным в сопровождении.

---

# Основные принципы

При разработке проекта необходимо придерживаться следующих принципов:

- простота важнее сложности;
- использовать стандартные возможности WordPress;
- не писать код "на будущее";
- не усложнять архитектуру без необходимости;
- каждая новая функция должна решать реальную задачу пользователя.

---

# Требования к коду

Код должен соответствовать:

- WordPress Coding Standards (WPCS);
- PSR-4;
- существующей архитектуре проекта.

Необходимо использовать:

- WordPress API;
- Composer Autoload;
- существующую структуру каталогов.

---

# Структура проекта

При добавлении новых файлов необходимо соблюдать существующую структуру проекта.

Например:

```
src/
assets/
templates/
languages/
docs/
```

Не следует создавать новые каталоги без необходимости.

---

# Работа с Git

Основные ветки проекта:

```
main
```

Содержит стабильные версии.

```
develop
```

Основная ветка разработки.

Все новые функции сначала разрабатываются в `develop`.

---

# Коммиты

Каждый коммит должен решать одну логически завершённую задачу.

Допускается:

- новая функция;
- исправление ошибки;
- обновление документации;
- рефакторинг.

Не допускается объединять несколько различных задач в одном коммите.

---

# Сообщения коммитов

Рекомендуется использовать понятные сообщения.

Примеры:

```
feat: add shortcode renderer

fix: validate pdf selection

docs: update architecture

refactor: simplify media dialog
```

Сообщение должно кратко описывать выполненную работу.

---

# Новые функции

Перед добавлением новой функции необходимо убедиться, что:

- она соответствует целям проекта;
- не усложняет архитектуру;
- не нарушает обратную совместимость;
- не требует необоснованных зависимостей.

---

# Изменение архитектуры

Любое изменение архитектуры должно сопровождаться обновлением:

- ARCHITECTURE.md
- DECISIONS.md

При необходимости также обновляются:

- HANDOFF.md;
- SPECIFICATION.md;
- ROADMAP.md.

---

# Документация

Если изменение влияет на поведение проекта, необходимо обновить соответствующую документацию.

Документация является частью проекта и поддерживается в актуальном состоянии.

---

# Использование сторонних библиотек

Добавление сторонних библиотек допускается только при наличии объективной необходимости.

Перед добавлением необходимо оценить:

- размер зависимости;
- активность поддержки;
- совместимость;
- реальную пользу.

Если задачу можно решить средствами WordPress или PHP, следует предпочесть этот вариант.

---

# Обратная совместимость

При разработке необходимо сохранять совместимость с существующими версиями проекта.

Изменение публичного API допускается только при наличии веских причин.

---

# Pull Request

Перед созданием Pull Request рекомендуется проверить:

- код соответствует WPCS;
- проект собирается без ошибок;
- документация обновлена;
- изменения протестированы;
- отсутствуют лишние файлы.

---

# Проверка перед коммитом

Перед каждым коммитом рекомендуется убедиться, что:

- код работает;
- отсутствуют предупреждения PHP;
- удалён временный код;
- удалены отладочные выводы;
- документация обновлена при необходимости.

---

# Что не рекомендуется

Не рекомендуется:

- выполнять большие рефакторинги без обсуждения;
- менять архитектуру без необходимости;
- смешивать несколько задач в одном коммите;
- дублировать существующий код;
- использовать нестандартные решения без веской причины.

---

# Принцип проекта

Главный принцип разработки:

> Простое решение лучше сложного.

Если существует несколько вариантов реализации, предпочтение отдаётся наиболее простому и понятному решению.

---

# Связанные документы

Перед началом работы рекомендуется ознакомиться со следующими документами:

- HANDOFF.md
- ARCHITECTURE.md
- SPECIFICATION.md
- DECISIONS.md
- ROADMAP.md
- AI_CONTEXT.md

---

# Статус документа

Документ является "живым".

При изменении процесса разработки он должен обновляться одновременно с изменением внутренних правил проекта.
