# Назначение документа

В этом документе фиксируются ключевые архитектурные решения проекта.

Его цель — объяснить не только **что** было сделано, но и **почему** было принято именно такое решение.

Это позволяет:

- быстрее понимать архитектуру проекта;
- избежать повторного обсуждения уже принятых решений;
- упростить сопровождение проекта;
- сохранить единый стиль разработки.

Каждое решение оформляется как ADR (Architecture Decision Record).

# ADR-001 — Использование WordPress Media Library

**Статус:** Accepted

## Контекст

Плагину необходимо хранить PDF-документы и файлы электронной подписи (`.sig`).

Рассматривались два варианта:

1. Собственное файловое хранилище.
2. Стандартная Media Library WordPress.

## Решение

Использовать исключительно стандартную WordPress Media Library.

## Причины

- полная совместимость с WordPress;
- использование стандартного API;
- отсутствие дублирования файлов;
- удобное резервное копирование;
- совместимость с плагинами миграции сайта.

## Последствия

Плагин не хранит собственные копии документов.

Все операции выполняются через WordPress API.

# ADR-002 — Использование attachment_id

**Статус:** Accepted

## Контекст

Необходимо хранить информацию о выбранных документах.

Возможные варианты:

- URL файла;
- путь к файлу;
- attachment_id.

## Решение

Использовать только `attachment_id`.

## Причины

- URL может измениться;
- путь зависит от структуры сайта;
- attachment_id является стандартным идентификатором WordPress.

## Последствия

Получение ссылок всегда выполняется через WordPress API.

# ADR-003 — Classic Editor как основной редактор

**Статус:** Accepted

## Контекст

Проект должен работать в существующих установках WordPress.

Большое количество сайтов продолжает использовать Classic Editor.

## Решение

Первая версия ориентирована на Classic Editor.

Поддержка Gutenberg рассматривается как отдельное расширение.

## Причины

- простота реализации;
- совместимость;
- отсутствие лишней сложности;
- соответствие текущим требованиям проекта.

## Последствия

Архитектура должна позволять добавить поддержку Gutenberg без нарушения существующей функциональности.

# ADR-004 — Shortcode как публичный API

**Статус:** Accepted

## Контекст

Необходимо определить способ публикации документов.

Варианты:

- собственный блок;
- HTML-вставка;
- shortcode.

## Решение

Использовать shortcode.

Пример:

```text
[ecp_document title="Документ" pdf_id="123" sig_id="456"]
```

## Причины

- встроенная возможность WordPress;
- совместимость;
- простота использования;
- стабильность.

## Последствия

Структура shortcode считается публичным API проекта.

Её изменение должно быть обратно совместимым.

# ADR-005 — Composer и PSR-4

**Статус:** Accepted

## Контекст

Необходимо организовать загрузку PHP-классов.

## Решение

Использовать Composer и стандарт PSR-4.

## Причины

- современный подход;
- отсутствие ручного подключения файлов;
- масштабируемость проекта;
- понятная структура.

## Последствия

Все новые классы должны соответствовать PSR-4 и автоматически загружаться через Composer.

# ADR-006 — Минимум зависимостей

**Статус:** Accepted

## Контекст

Любая внешняя библиотека увеличивает сложность сопровождения.

## Решение

Не использовать сторонние библиотеки без объективной необходимости.

## Причины

- снижение сложности;
- повышение надёжности;
- меньше потенциальных конфликтов;
- проще обновление.

## Последствия

По возможности используются стандартные средства WordPress и PHP.

# ADR-007 — Разделение ответственности

**Статус:** Accepted

## Контекст

Проект должен оставаться понятным и поддерживаемым.

## Решение

Разделить ответственность между компонентами.

- PHP — бизнес-логика.
- Templates — HTML.
- CSS — оформление.
- JavaScript — интерактивность.

## Причины

- читаемость;
- удобство сопровождения;
- простота тестирования.

## Последствия

Не рекомендуется смешивать HTML, CSS, JavaScript и бизнес-логику в одном файле.

# ADR-008 — Один коммит — одна задача

**Статус:** Accepted

## Контекст

История Git должна быть понятной.

## Решение

Каждый коммит реализует только одну логически завершённую задачу.

## Причины

- проще искать ошибки;
- легче выполнять откат;
- понятнее история изменений.

## Последствия

Не допускается объединять в одном коммите:

- новую функциональность;
- исправление ошибок;
- рефакторинг.

# ADR-009 — Простота важнее сложности

**Статус:** Accepted

## Контекст

Проект предназначен для длительной эксплуатации.

## Решение

При наличии нескольких рабочих вариантов выбирать наиболее простое решение.

## Причины

- проще сопровождение;
- ниже вероятность ошибок;
- понятнее код;
- легче подключить нового разработчика.

## Последствия

Не допускается усложнение архитектуры без объективной необходимости.

# Как принимать новые решения

Если в ходе разработки принимается новое архитектурное решение, рекомендуется:

1. Добавить новый ADR в этот документ.
2. Кратко описать контекст.
3. Зафиксировать принятое решение.
4. Указать причины выбора.
5. Описать последствия.

Это позволит сохранить историю развития архитектуры проекта.
