# Назначение документа

Этот документ предназначен для ИИ-ассистентов (ChatGPT, Codex, Claude, Gemini, GitHub Copilot и других), участвующих в разработке проекта **ECP Documents**.

Перед внесением изменений рекомендуется ознакомиться с этим документом и связанными материалами проекта.

Цель — сохранить единую архитектуру, стиль разработки и качество кода.

---

# О проекте

ECP Documents — плагин WordPress для публикации PDF-документов с файлами электронной подписи (`.sig`).

Плагин должен быть:

- простым;
- понятным;
- совместимым со стандартным WordPress API;
- удобным в сопровождении;
- без лишних зависимостей.

---

# Основные цели

При работе над проектом необходимо стремиться к следующим целям:

- простота реализации;
- читаемость кода;
- предсказуемое поведение;
- совместимость с WordPress;
- обратная совместимость между версиями.

---

# Перед началом работы

Перед внесением изменений рекомендуется ознакомиться со следующими документами:

1. `HANDOFF.md`
2. `ARCHITECTURE.md`
3. `SPECIFICATION.md`
4. `DECISIONS.md`
5. `ROADMAP.md`
6. `CONTRIBUTING.md`

Если предлагаемое изменение противоречит одному из этих документов, сначала следует обновить документацию, а затем код.

---

# Архитектурные правила

Необходимо соблюдать существующую архитектуру проекта.

Следует использовать:

- Composer;
- PSR-4;
- WordPress API;
- существующую структуру каталогов.

Не рекомендуется:

- менять структуру проекта без необходимости;
- переносить бизнес-логику в шаблоны;
- смешивать PHP, HTML, CSS и JavaScript в одном файле.

---

# Работа с WordPress

Предпочтительно использовать стандартные возможности WordPress.

Например:

- Media Library;
- Shortcode API;
- Settings API;
- функции экранирования и санитизации;
- локализацию WordPress.

Не следует заменять стандартные механизмы собственными решениями без объективной необходимости.

---

# Работа с кодом

При написании кода рекомендуется:

- соблюдать WordPress Coding Standards (WPCS);
- использовать понятные имена переменных и методов;
- избегать дублирования;
- писать компактные методы с одной зоной ответственности;
- использовать существующие компоненты проекта, если они уже решают необходимую задачу.

---

# Работа с зависимостями

Не добавлять сторонние библиотеки, если задача может быть решена средствами WordPress или PHP.

Каждая новая зависимость должна быть обоснована.

---

# Работа с Git

Предпочтительный порядок работы:

1. Одна логическая задача.
2. Один коммит.
3. Понятное сообщение коммита.
4. Обновление документации при необходимости.

---

# Работа с документацией

Если изменение влияет на:

- архитектуру;
- публичный API;
- процесс разработки;
- функциональность,

необходимо обновить соответствующие документы в каталоге `docs/`.

Документация считается частью проекта и должна оставаться актуальной.

---

# Что не следует делать

Без объективной необходимости не следует:

- переписывать архитектуру;
- менять публичный API;
- изменять структуру каталогов;
- добавлять новые зависимости;
- выполнять масштабный рефакторинг;
- внедрять сложные абстракции;
- использовать нестандартные решения, если существует стандартный механизм WordPress.

---

# Приоритеты при принятии решений

При наличии нескольких вариантов реализации рекомендуется выбирать решение, которое:

1. проще;
2. понятнее;
3. лучше соответствует WordPress;
4. требует меньше сопровождения;
5. не нарушает существующую архитектуру.

---

# Контрольный список

Перед завершением задачи рекомендуется проверить:

- [ ] Код соответствует WPCS.
- [ ] Не нарушена архитектура проекта.
- [ ] Используется WordPress API.
- [ ] Не добавлены лишние зависимости.
- [ ] Нет отладочного кода.
- [ ] Документация обновлена при необходимости.
- [ ] Изменение решает одну конкретную задачу.

---

# Основной принцип проекта

Главная цель проекта — не максимальное количество функций, а качественная, понятная и долговечная реализация.

Если существует выбор между сложным и простым решением, предпочтение следует отдавать простому.
